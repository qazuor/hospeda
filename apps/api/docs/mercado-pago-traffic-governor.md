# Mercado Pago traffic governor (HOS-1999)

`HOSPEDA_MERCADO_PAGO_GOVERNOR_MODE` controls the process-wide traffic governor. `off` disables it, `observe` (the default) measures requests and virtual waits without changing request behavior, and `enforce` admits each HTTP attempt through the token bucket and makes the governor the owner of read retry pacing. In `enforce`, L1 keeps a three-attempt maximum: 429 waits happen in the next token acquisition, interactive reads include token waits in a 4 s budget, and background reads use the cron signal. The sweep's L2 decorator does not retry rate limits and retries 5xx/network failures twice total; legacy retry behavior remains active in `off` and `observe`.

In `enforce`, a dedicated Redis client shares the maximum `mp:cooldown-until` deadline through the existing `HOSPEDA_REDIS_URL`. Reads are cached for at most 250 ms and bounded to 50 ms; when Redis is unavailable the governor uses its in-process deadline and records `redisFallbacks`. Redis connection and read failures fail open and are logged once per outage, with one recovery log. Without `HOSPEDA_REDIS_URL`, enforce uses an in-process cool-down.

The webhook defers a rate-limited read only in `enforce`, returning 503 with `Retry-After` set to the remaining cool-down, rounded up and clamped to 1–120 seconds. An incomplete read remains deferred with `Retry-After: 60`. In `off` and `observe`, the existing rate-limited-read behavior remains a 500 with no `Retry-After`.

The governor emits one `mp_traffic_window` structured log per traffic class every 60 seconds when that class had traffic. Interactive 429 responses are logged at warning level with capture enabled; cron traffic is also summarized in each affected cron run's `details.providerTraffic`, including memo hits and Redis fallbacks.
